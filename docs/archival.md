# Теги, PDF/A и гибридные счета

## Tagged PDF

Дерево логической структуры строится во время рисования: только тогда известен порядок, в котором
содержимое ложится на страницу, и никакой последующий разбор его не восстановит.

```csharp
Report.Create()
    .Page(page =>
    {
        page.Tagged("ru-RU");
        page.Content().Column(column =>
        {
            column.Item().Text("Заголовок", TextStyle.Default.FontSize(18).Bold());
            column.Item().Text("Абзац текста.");
            column.Item().Table(table => { … });
        });
    })
    .Render(document);
```

Текст размечается как `P`, картинки — как `Figure` с альтернативным текстом, таблицы — как
`Table` / `TR` / `TH` / `TD`. Содержимое привязывается к дереву через `BDC`/`EMC` с `MCID`,
страницы получают `/StructParents`, каталог — `/StructTreeRoot`, `/MarkInfo` и `/Lang`.

Тег абзаца настраивается: `element.SemanticTag = "H1"`. Для собственной разметки есть
`TaggingSession.Group` и `TaggingSession.Marked`, а декорации, которые не должны попадать в чтение
вслух, оборачиваются в `TaggingSession.Artifact`.

Дерево можно строить и без компоновщика — `Inkwright.Tagging.StructureTreeBuilder` работает поверх
любого документа.

## PDF/A

```csharp
using Inkwright.Layout;

PdfAProfile.Apply(document, PdfAConformance.A2B, new PdfAOptions { Language = "ru-RU" });
document.Save("archival.pdf");
```

Уровни частей 1–3: `A1B`, `A1A`, `A2B`, `A2U`, `A2A`, `A3B`, `A3U`, `A3A` — три части ISO 19005 и три
уровня соответствия. Часть 1 написана по PDF 1.4, поэтому заявка на неё пришпиливает версию 1.4, и
писатель перестаёт использовать объектные потоки и потоки перекрёстных ссылок, которых в 1.4 ещё не
было; это касается и `SaveIncremental` — дописанная секция файла 1.4 остаётся классической таблицей
`xref`. Уровень A требует дерева структуры — для него страница должна быть размечена через
`page.Tagged(...)`.

### PDF/A-4: другая конструкция, а не ещё один уровень

`A4`, `A4E`, `A4F` — часть 4 (ISO 19005-4:2020), единственная написанная против PDF 2.0.

```csharp
PdfAProfile.Apply(document, PdfAConformance.A4, new PdfAOptions { Language = "ru-RU" });
```

Что здесь устроено иначе:

- **Уровней A, U и B нет.** Есть базовый `A4` и два расширения — `A4E` (трёхмерная графика, Annex B)
  и `A4F` (вложенные файлы любого типа, Annex A). Они не градуируют строгость, а добавляют
  разрешения: то, что запрещено в `A4`, в них становится можно.
- **Заголовок `%PDF-2.n`** (§6.1.2). Части 1–3 требуют `%PDF-1.n`, поэтому **ни один файл не может
  заявить одновременно часть 4 и любую из предыдущих** — это взаимоисключающие требования к первым
  восьми байтам.
- **Словаря информации о документе не будет** (§6.1.3): PDF 2.0 объявил его устаревшим, часть 4
  сделала это нормативным. Профиль убирает его и перестаёт штамповать туда `Producer` при каждом
  сохранении; заголовок, автор и даты живут в XMP-пакете, куда `Apply` их и переносит. Исключение
  одно — документ с `PieceInfo` в каталоге, где словарь допустим ради `ModDate`.
- **Дерево структуры не требуется ни на одном уровне** (§6.8 лишь рекомендует его и отсылает к
  ISO 14289), как и обратное чтение текста: `ToUnicode` в §6.2.10.7 сформулирован через «should».
  Размечать документ по-прежнему стоит — просто это больше не условие архивного заявления.
- **JavaScript разрешён в файле** (§6.6.2): ограничение перенесено на обработчик, который вправе
  выполнить действие только по явному требованию человека.
- **Заявка выглядит иначе** (§6.7.3): `pdfaid:part` равен 4, добавляется обязательный `pdfaid:rev`
  с четырёхзначным годом ревизии, а `pdfaid:conformance` пишется **только** для `A4E` и `A4F`.
  У базового `A4` этого свойства быть не должно, и валидатор об этом сообщит.

Профиль добавляет то, чего требует стандарт: output intent с ICC-профилем sRGB, идентификатор файла,
XMP-метаданные, согласованные с информационным словарём, заявку `pdfaid:part` и `pdfaid:conformance`.
ICC-профиль генерируется, а не лежит бинарным блобом: sRGB — это несколько сотен байт хорошо
описанной структуры, и написать её кодом честнее, чем прятать в ресурсах.

Заявка запоминается в документе: попытка сохранить его с шифрованием после этого отклоняется, потому
что шифрование запрещено всеми четырьмя частями — часть 4 делает это через запрет ключа `Encrypt`
в трейлере (§6.1.3). Это относится и к загруженным файлам — их заявка
читается из `pdfaid` в XMP-пакете, так что зашифровать чужой PDF/A, «не заметив» его статуса,
не выйдет.

Сохранение не рассинхронизирует метаданные. Каждый `Save` штампует в информационный словарь дату
изменения и имя производителя — и тут же правит те же значения в XMP-пакете (`xmp:ModifyDate`,
`xmp:MetadataDate`, `pdf:Producer`), если пакет их содержит. Иначе архивный файл переставал бы
соответствовать части 1 (§6.7.3, согласие DocInfo и XMP) в момент любого пересохранения.

## Проверка

`Apply` проверяет документ и отказывается ставить заявку, которую тот не выдерживает:

```
The document does not satisfy PDF/A-2b:
  6.2.11.4.1: The font 'Helvetica' is not embedded. PDF/A has no built-in fonts, so even
  Helvetica has to travel with the file.
```

Ту же проверку можно запустить отдельно — над моделью, над байтами или над файлом:

```csharp
foreach (PdfAProblem problem in PdfAProfile.ValidateFile("report.pdf", PdfAConformance.A2U))
    Console.WriteLine($"{problem.Clause}: {problem.Message}");
```

Каждая находка названа пунктом стандарта, который она нарушает, — так её можно найти в тексте и
сопоставить с вердиктом стороннего валидатора.

Что именно проверяется по каждому пункту, перечислено в матрицах соответствия — отдельно для
[частей 1–3](pdfa-matrix.md) и для [части 4](pdfa4-matrix.md), потому что требования расходятся
с первых байтов файла. Коротко: структура файла и её байтовый синтаксис, фильтры,
лимиты реализации, output intent и ICC-профиль, устройство-зависимый цвет против профиля, состояние
графики, прозрачность по Annex A, шрифты (встраивание, `CIDSet`, ширины против программы шрифта,
кодировки TrueType, `ToUnicode`, `.notdef`), аннотации, формы, действия, XMP и extension-схемы,
дерево структуры для уровня A, вложения, необязательное содержимое и требования Annex B к подписям.

Проверено на 106 архивных файлах из тестового набора iText, которые заявляют части 1–3: все они
признаются соответствующими своей заявке. Полную формальную проверку по-прежнему делает veraPDF —
часть требований (например, законность встраивания шрифта или соответствие вложенного PDF)
из файла в принципе не выводится.

Вложения разрешены только в третьей части: вторая допускает вложенные файлы, лишь если они сами
соответствуют PDF/A, поэтому XML-счёт рядом с заявкой на часть 2 профиль отклоняет.

## Factur-X и ZUGFeRD

Гибридный счёт — это страница для человека и XML для машины в одном файле:

```csharp
document.Attachments.AddFacturX(invoiceXml);                       // factur-x.xml, профиль EN 16931
document.Attachments.AddFacturX(invoiceXml, "zugferd-invoice.xml", "EXTENDED");

PdfAProfile.Apply(document, PdfAConformance.A3B);
```

Вложение получает `/AFRelationship /Data`, попадает в дерево имён `/EmbeddedFiles` и в массив
`/AF` каталога, а в XMP добавляется схема `fx:` с именем файла, версией и уровнем соответствия —
ровно то, по чему обработчик счетов находит данные.

Читаются вложения так же просто:

```csharp
foreach (string name in document.Attachments.Names)
    Console.WriteLine(name);

byte[]? xml = document.Attachments.Read("factur-x.xml");
```

Любой файл можно приложить и без Factur-X:

```csharp
document.Attachments.Add("source.csv", bytes, "text/csv", "Исходные данные", AttachmentRelationship.Source);
document.Attachments.AddFile(@"C:\data\report.xlsx", "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet");
```
